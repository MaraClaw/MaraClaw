# Chat-turn stress test at 2,000 agents (2026-11-12)

The database work behind a chat turn was stress-tested with 2,000 agents and 10 million rows in each history table. After the four database fixes there were **no deadlocks**, and mixed-workload throughput rose **from 1,229 to 4,738 tps (about 3.9x)**. In the recorded run every workload got faster at every percentile, and the dispatch reconciler, which had fallen seconds behind its one-second schedule, finished every tick in under a second.

## Test hardware

| Component | Spec |

| Machine | MacBook Air (Mac17,3), macOS 27.2 |
| CPU | Apple M5, 10 cores (4 Super + 6 Efficiency) |
| Memory | 16 GB unified |
| Storage | 494 GB internal SSD, which also holds the Docker VM disk |
| Docker | Docker Desktop 4.99.0, Engine 29.9.3. Linux VM (aarch64, kernel 7.0.14-linuxkit) with **10 vCPUs and 8 GB RAM** |
| Database | `postgres:18.6-alpine` with `shared_buffers=512MB`, `work_mem=8MB`, `max_connections=300`. `fsync`, `full_page_writes` and `synchronous_commit` were off, with `wal_level=minimal` |
| Load generator | `pgbench`, run inside the database container, so it shared the same vCPUs |

## Workload

| Dimension | Value |
|---|---|
| Tenants and agents | 20 tenants and 2,000 agents, each agent with its own owner |
| Sessions | 20,000 web chat sessions and 20,000 reply bindings (10 per agent) |
| History | 10 M rows each in `gateway_messages`, `chat_messages` and `chat_history_changes` (6.8 GB) |
| Dispatch queue | 22,000 pending and 2,000 in-flight turns, then a backlog phase with 184,000 pending |
| Load | 64 clients, 8 threads, 60 s: 40% chat intake, 40% claim + settle, 20% history read, plus one reconciler tick per second |
| Comparison | Before: the pre-fix schema and SQL. After: the current baseline and SQL |

## The four fixes

| # | Problem | Fix |
|---|---|---|
| 1 | Chat intake locked the chat session before the agent, while claims and settlements lock the agent first, so they deadlocked | `lock_for_agent` takes the agent `FOR KEY SHARE` before the session `FOR UPDATE`. The expiry check inside the turn transaction no longer writes |
| 2 | Every reconciler tick read and sorted the whole pending queue | Partial index `ix_gateway_messages_pending_order`, plus a fixed lower bound for the first page so the index can still seek when PostgreSQL reuses a cached generic plan |
| 3 | The recent-history read sorted the whole conversation (510 buffers) | `ix_chat_messages_agent_conv_created` (55 buffers) |
| 4 | The agent gateway listing scanned all 10 M rows | `ix_gateway_messages_agent_created` |

## Reproduced with the bundled script

`run-stress.sh` reran the full 2,000-agent scenario on the same machine. It exited 0 in 713 s and every check passed:

- Deadlocks went from 9 to 0.
- Throughput went from 672 to 1,329 tps.
- History read p50 dropped from 280 to 7.2 ms.
- Reconciler tick p50 dropped from 1,230 to 300 ms.

Absolute numbers were lower than in the recorded run. The MaraClaw dev stack was running in the same 8 GB VM, and the bundled scripts model more of the code: every intake updates its owner's quota row, and every settlement updates the agent's last-seen time. Query plans matched the recorded run, and buffer counts came out close.

Intake and claim medians rose in this run: intake from 14 to 35 ms, claims from 16 to 40 ms. pgbench keeps a fixed number of clients busy, so clients no longer stuck on history reads moved to intake and claims, while total throughput doubled. The regression-test runner passed 56 tests, none skipped.

## Caveats

- The test covers database work only, with durability off. It leaves out Redis, HTTP/WebSocket handling, auth reads and the guest `docker exec`. Compare before with after, not with production timings.
- Throughput varied by up to 2x between repeated runs of the same setup, so treat 3.9x as a rough guide. The MacBook Air has no fan, so heat during long runs is a likely cause; that was not measured.
- The three indexes are baseline objects with no separate upgrade. A bootstrap rerun builds them on an existing database with a plain `CREATE INDEX`, which blocks writes to the table while it runs. `ix_chat_messages_agent_conv_created` takes about 825 MB per 10 M chat messages and `ix_gateway_messages_agent_created` about 390 MB per 10 M gateway rows, so on large production tables build them first with `CREATE INDEX CONCURRENTLY IF NOT EXISTS` and the baseline definitions.

## Open items

- The other query in each reconciler tick, `delivered_dispatch_page`, takes 18 ms and 60,000 buffers, and its cost grows with the number of reply bindings.
- Once the reconciler passes the last lane head, the next page still reads every pending row after it (256 ms with 153,000 rows), once per reconciler cycle.
- `test_chat_history_postgres.py`, which covers fix 3, is not in CI's `lifecycle-postgres` list.
