# Chat-turn database stress test: 2026-11-12

On 2026-11-12 the database work behind a chat turn was stress-tested at 2,000 agents with 10 million rows in each history table. The test drove intake, native dispatch claims and settlements, history reads, the dispatch reconciler and the agent gateway listing against PostgreSQL 18.6. It found four problems. With all four fixed, the same workload ran with no deadlocks at nearly four times the throughput. [`README.md`](README.md) explains how to reproduce and check this result.

## Summary

| # | Finding | Fix | Recorded effect |
|---|---|---|---|
| 1 | Chat intake deadlocked with native claims and settlements | `ChatSessionDAO.lock_for_agent` takes the agent row `FOR KEY SHARE` before the session `FOR UPDATE`; the expiry check inside `accept_submission` no longer writes | 33 deadlocks in 73,801 transactions, then none in 284,395 |
| 2 | Every reconciler tick read every pending row | `ix_gateway_messages_pending_order` and a row-bound keyset start in `pending_dispatch_page` | First page at 184,000 pending: 399.6 ms to 0.62 ms. Tick p50 under load: 2,494 ms to 236 ms |
| 3 | Recent-history reads sorted the whole conversation | `ix_chat_messages_agent_conv_created` | 510 to 55 buffers per read. p50 under load: 89.7 ms to 1.4 ms |
| 4 | The agent gateway listing scanned the whole table | `ix_gateway_messages_agent_created` | 0.55–2.36 s to 0.03–0.18 ms |

Mixed-workload throughput went from 1,228.7 to 4,737.6 transactions per second. Treat that ratio as a rough guide: on this machine, repeated runs of one configuration drifted by up to a factor of two.

## Findings

### 1. Intake deadlocked with native claims and settlements

`chat_submissions.accept_submission` locked the chat session first, through `chat_session_dao.lock_for_agent` (`FOR UPDATE`). Its chat and gateway inserts then took the agent row's foreign-key lock (`FOR KEY SHARE`). Native claims (`claim_ordinary_turn`) and settlements (`settle_native_report`) lock the agent `FOR UPDATE` first and the session second: a claim through `bind_openclaw_reply`, a settlement through the history trigger on its assistant message. The opposite orders formed cycles. PostgreSQL waited `deadlock_timeout` (1 s), aborted one side, and that turn failed.

`lock_for_agent` now runs `SELECT 1 FROM agents WHERE id = ... FOR KEY SHARE` before the session lock. Every caller therefore locks tenant, subject, agent and then session, the same order that claims and settlements use. `FOR KEY SHARE` conflicts only with `FOR UPDATE`, so intakes do not queue behind each other or behind plain agent updates.

The expiry check inside `accept_submission` now passes `mark=False`. Marking an expired agent takes exclusive tenant and agent locks, which here would come after the session lock. The raise that follows rolled the mark back anyway; the WebSocket quota check that runs before the transaction still persists it.

Evidence:

- In the discovery run, adding only the agent `FOR KEY SHARE` to the intake script took deadlocks from 20 and 19 to 0 and 0, in two runs of each arm from the same reset state.
- In the recorded run, deadlocks went from 33 (15 in intakes, 18 in claims or settlements) to none.
- Before the fix, both cases of `test_submission_locks_the_agent_before_the_session_native_work_writes` (claim and settle) failed with `deadlock detected`. After the fix, both pass.

Each deadlock also stalls the clients queued behind the same agent for that second. At `--quick` scale (64 clients, 200 agents), about 30 claims queued on one agent row and transactions waited up to 63 s. After the fix, the slowest transaction took 1.3 s.

### 2. Every reconciler tick read every pending row

`gateway_message_dao.pending_dispatch_page` returns the next 50 lane heads in `(created_at, id)` order. The only pending index leads with `(agent_id, conversation_id)`. So every tick bitmap-scanned all pending rows, ran the older-pending probe for each one and sorted them all before keeping 51. The cost grew with the whole queue rather than the page: a page took 0.4 s at 184,000 pending on an idle database. Under load the one-second tick fell behind, with p50 2.5 s and p95 9.3 s.

The first page used `%(after_time)s IS NULL OR (created_at, id) > ...`. psycopg prepares a statement on the server from its fifth execution, and PostgreSQL may then pick a generic plan. In a generic plan the `IS NULL OR` cursor is only a filter, so the walk restarts at the start of any index.

`scripts/schema_baseline.sql` adds `ix_gateway_messages_pending_order ON gateway_messages (created_at, id) WHERE status = 'pending'`. `pending_dispatch_page` now starts from a row bound below every row (`_DISPATCH_START`), so the cursor is always an index condition. A page walks the index from its cursor and stops at its 51st head.

The page after the last head still walks every pending row behind it: 256 ms with 153,000 rows behind the last head. It now runs once per reconciler cycle instead of on every tick.

### 3. Recent-history reads sorted the whole conversation

`chat_message_dao.list_recent` reads the newest 50 messages of one agent's conversation. The planner combined `ix_chat_messages_conversation_id` and `ix_chat_messages_agent_id` in a BitmapAnd and sorted the whole conversation. For a 500-message conversation that read 510 buffers and took 44 ms when cold. An ordered walk of `ix_chat_messages_conv_created_id` reads 55 buffers, but the planner estimated one matching row and never chose it. Dependency statistics on `(agent_id, conversation_id)` corrected the estimate to 497 rows but left the plan unchanged, because PostgreSQL costs a BitmapAnd as if its inputs were independent.

`scripts/schema_baseline.sql` adds `ix_chat_messages_agent_conv_created ON chat_messages (agent_id, conversation_id, created_at DESC)`, which also serves `list_for_agent_conversation`. It adds no extended statistics: with them in place, the planner still chose the BitmapAnd.

### 4. The agent gateway listing scanned the whole table

`GET /api/agents/{agent_id}/gateway-messages` runs `gateway_message_dao.list_recent`: the newest 50 rows of one agent in any status, ordered `created_at DESC NULLS LAST`. No index leads with `agent_id` across statuses, so each call scanned all 10 million rows in parallel: about 250,000 buffers and 0.55–2.36 s. `scripts/schema_baseline.sql` adds `ix_gateway_messages_agent_created ON gateway_messages (agent_id, created_at DESC NULLS LAST)`.

Before the fix: 672.1 tps and 9 deadlocks. After: 1,329.3 tps and none.

The plans, buffer counts and the direction of every change match the recorded run. The absolute numbers differ for three reasons:

- The machine was busier. The MaraClaw development stack (engine, web-e and an agent container) ran in the same 8 GB Docker VM, which left less memory for caching. Seeding took 456 s instead of 254 s, and cold reads were slower.
- The scripts model the code more closely than the ad hoc bench of the recorded run. Every intake takes its owner's quota row lock, because seeded quotas cannot run out. Every settlement updates the agent's `openclaw_last_seen`, as `_finalize_report` does.
- pgbench runs a closed loop. Before the fix, slow history reads held most clients. After the fix those clients moved to intakes and claims, where row-lock contention and latency rose (intake p50 went from 14.4 to 34.8 ms) while total throughput doubled.

Two `--quick` runs (200 agents, 1,000,000 rows per table) had 379 and 430 deadlocks before the fix and none after. Throughput went from 759 to 2,392 tps in one and from 1,258 to 2,998 tps in the other.

## Cost and rollout

| Index | Size |
|---|---|
| `ix_chat_messages_agent_conv_created` | 825 MB for 10,000,000 messages |
| `ix_gateway_messages_agent_created` | 388–394 MB for 10,024,000 rows |
| `ix_gateway_messages_pending_order` | 0.9 MB at 22,000 pending rows, 7.3 MB at 184,000; it holds pending rows only |

Each `gateway_messages` write now maintains two more indexes, and each `chat_messages` insert one more. The after-fix throughput includes that cost.

The three indexes are baseline objects with no separate upgrade. Fresh databases get them at initialization. Existing databases get them through `CREATE INDEX IF NOT EXISTS` at the next `python -m app.scripts.bootstrap_db` rerun; in the reproduction, that rerun built all three on the 10-million-row database in 30 s. A plain `CREATE INDEX` blocks writes to its table while it builds. On a large production table, first create the three indexes with `CREATE INDEX CONCURRENTLY IF NOT EXISTS` and the baseline definitions, so the rerun skips them. [`../chat-history.md`](../chat-history.md) and [`../shared-openclaw-runtime.md`](../shared-openclaw-runtime.md) carry the same note.

## Verification of the fixes

- `run-regression-tests.sh` (the five tests that pin the fixes, plus the rest of their files): 56 passed, none skipped.
- The live PostgreSQL suite (the CI `lifecycle-postgres` list plus the chat, OpenClaw, gateway and burst PostgreSQL tests): 739 passed. The 14 failures, in `test_gateway_report_credentials_postgres.py` and `test_gateway_report_relay_postgres.py`, fail the same way without these changes.
- The unit suite (`bash scripts/test.sh`): 10,640 passed. Its one failure, in `test_start_from_docker.py`, came from an unrelated uncommitted launcher change and passes now that the launcher is fixed.
- Ruff check and format, basedpyright, ty, the API contract check and both freeze scripts were clean.
