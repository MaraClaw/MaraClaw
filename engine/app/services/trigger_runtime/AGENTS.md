# app/services/trigger_runtime

This package is the queued trigger execution runtime. It is coupled to agents, chat sessions, OKR automation, websocket delivery, audit logs, and A2A behavior.

## Startup Path

- `app.runtime.lifecycle.Runtime.start()` starts `trigger_daemon.start_trigger_daemon()` only when `PROCESS_ROLE` includes `all` or `worker`.
- Do not move trigger scheduling into ordinary API processes. Duplicate workers increase scheduling pressure even though DB claiming mitigates execution duplication.
- `trigger_daemon.py` owns the 15-second trigger loop; the worker lifecycle separately owns the 60-second heartbeat loop.
- `scan.py` (`TriggerScanner`) reads only the triggers that are due through `agent_trigger_dao.list_due_page` (keyset pages by `(next_due_at, id)` over the partial index `ix_agent_triggers_due`, never larger than the free slots; each `DueTrigger` carries its agent's effective timezone, so the tick runs no timezone query) and owns at most `MAX_CONCURRENT_EVALUATIONS` tasks. Its cursor persists across ticks and wraps when a page comes back short, so a trigger deferred for capacity is read on a later tick and hung ones cannot starve later rows. A tick waits `EVALUATION_SETTLE_SECONDS` in total, not per page. `close()` cancels and awaits every owned task.
- `trigger_daemon.EVALUATION_DEADLINE_SECONDS` bounds only `_evaluate_trigger` (`_evaluate_within_deadline`). Never widen it to `_process_trigger`: `enqueue_due_trigger` owns the poll baseline transaction, so cancelling it loses the baseline write. A timed-out poll keeps its claimed checkpoint and waits for its next interval; a cron trigger catches up from `last_fired_at`. The daemon beats `loop_progress()` only after a tick finishes without raising (`PROGRESS_BUDGET_SECONDS`).
- `TRIGGER_MAX_CONCURRENT_INVOCATIONS` (default 8, 1 to 256, independent of `SCHEDULE_MAX_CONCURRENT_EXECUTIONS`) caps the trigger invocations one worker runs. `trigger_daemon.InvocationCapacity` is the ledger, replaced by every `open_trigger_admission`: reserved slots plus running invocations never exceed it. A tick reserves every free slot before its claim awaits the database and passes that count down as the agent-group budget, keeps one slot per leased agent as soon as the claim returns and gives the rest back. Each invocation returns its slot once from its done callback on completion, failure or cancellation; a terminal write whose commit is uncertain fails only the task, never the execution, and is left to lease recovery. A full tick (budget 0) still evaluates triggers and runs disabled-trigger recovery but leases nothing.
- Agent-to-agent wakes share that ledger. A wake reserves its slot before it consumes the chain depth or dedup window and holds it through the sender lookup. A wake that finds no free slot while a claim is unsettled waits for the claim to keep what it leased; if none is free then, it logs a capacity refusal and returns with no dedup or chain side effect (a wake has no durable queue).

## Module Responsibilities

- `evaluator.py` owns trigger condition semantics for `cron`, `once`, `interval`, `poll` and `on_message`, plus `schedule_timezone`, the zone a schedule is evaluated in. `poll_check` returns a `PollObservation` and never writes config.
- `queue.py` inserts `trigger_executions` rows (`TriggerExecutionRecord`) with idempotency keys and webhook payload handling.
- `dispatch.py` converts due triggers into queued executions (polls via `_enqueue_poll_observation`) and claims ready invocations grouped by agent.
- `executions.py` owns claiming, first-start accounting, fenced five-minute leases, the lease hold that renews and stops lost work, recovery, and runtime trigger cloning.
- `invoker.py` runs chat/LLM/delivery/audit inside the lease hold and its run budget, checks the hold before each side effect, confirms ownership after the LLM returns, joins the heartbeat, then writes fenced terminal status.
- `okr.py` owns the deterministic OKR firings (`daily_okr_collection`, `daily/weekly/monthly_okr_report`): the report period of a due firing, taken as the local day in the schedule's zone (`okr_daily_collection.local_day`), and the work an execution runs. `dispatch.enqueue_due_trigger` queues them like any trigger, keyed `okr:{trigger}:{period}` with the period in the payload (`okr_period`); `invoker.py` runs them under the lease and never sends them to the model. Nothing in the daemon, evaluator or API sends or generates for a due OKR trigger, and nothing reads the host's date: a retried run uses the stored period.
- `keys.py` builds deterministic idempotency keys and owns `poll_sequence` / `POLL_OBSERVED_KEY`.

## Invariants

- `agent_triggers.next_due_at` is the earliest instant `evaluate_trigger` can call the trigger due; `app/core/trigger_schedule.py` (`next_due_at`) is its only computation and mirrors the evaluator's rules (schedule, cooldown, `max_fires`, expiry, zone), so change both together. `AgentTriggerDAO.reschedule` recomputes it from the stored row inside the transaction of every write of a schedule input: `create`, `update` (any of type, config, `is_enabled`, `last_fired_at`, `fire_count`, `max_fires`, `cooldown_seconds`, `created_at`, `expires_at`), `merge_user_config`, `claim_poll_checkpoint`, `record_first_starts`, `mark_skipped`, and the cron reschedules of `AgentDAO.update` (timezone or tenant change) and `TenantDAO.update` (timezone change). The bulk disables set it to NULL. A new write of a schedule input must go through one of these or call `reschedule`; a row left with a stale value never fires again, silently. `webhook` rows have no schedule, `on_message` rows are always due.
- The legacy due-column upgrade also calls `reschedule` once, in the bootstrap transaction, for already-enabled triggers. Stop legacy trigger writers before upgrading; they do not maintain this column.
- OKR firings fail into a retry, not a refire. `invoker` records the error through `mark_trigger_executions_retry` (`TriggerExecutionDAO.retry_later`): the row goes back to `pending` with `scheduled_at` pushed `EXECUTION_RETRY_DELAY` ahead (the claim ignores pending rows until then), keeps `started_at` (so `fire_count` counts once and `last_fired_at` keeps the cron quiet) and fails for good once it first started `EXECUTION_RETRY_WINDOW` ago. Lease loss and a spent run budget still fail the row.
- A disable settles pending work: `AgentTriggerDAO.update` (every user, tool, seeder, expiry and on-message limiter disable) and the bulk `disable_for_tenant`/`disable_for_creator`/`disable_for_agent` fail the trigger's pending executions with `TRIGGER_DISABLED_ERROR` in the disabling transaction (`TriggerExecutionDAO.fail_pending_for_triggers`), so enabling it again never runs work that came due earlier. A self-disable (`self_disabled`) and processing rows are left alone; expired processing rows of a disabled trigger fail through `fail_abandoned_trigger_executions`. Any new disable path must go through these DAO methods.
- The claim reads live work through the partial `ix_trigger_executions_claimable` index (`pending` and `processing` rows only); keep the claim's status predicates inside that index predicate.
- Do not bypass `trigger_executions` for scheduled/webhook triggers. It provides idempotency, distributed claiming, and lease recovery.
- `try_enqueue` locks the trigger `FOR KEY SHARE`, then the agent `FOR KEY SHARE NOWAIT`, so it never waits on an agent delete that cascades back to the trigger. After `ENQUEUE_LOCK_ATTEMPTS` busy attempts it raises `LockNotAvailableError`, never `(None, False)`, which callers read as a duplicate; webhooks answer 503. Call it from a transaction that holds no other row locks.
- Each claim stores a unique lease token in `lease_owner`; renewal and terminal writes require `status = 'processing'` and that token.
- Claims lock executions and their trigger rows with `SKIP LOCKED` and never wait on a row lock. Trigger deletes lock the trigger before cascading to its executions, so a waiting claim can deadlock.
- A claim takes whole agent groups up to the budget and the 100-row ceiling: `TriggerExecutionDAO.claim_pending` locks the oldest unlocked ready row of an agent not chosen yet, then that agent's ready rows, and repeats. One agent's rows batch into one invocation, other agents' rows stay unlocked for peers, and no pending row or expired lease outside the chosen groups gains an owner.
- Renewal and completed/failed writes update one execution per transaction in a fresh context. Do not batch them or run them on an ambient `connection_ctx`.
- Heartbeats renew every `LEASE_RENEW_INTERVAL`; never hold a checkout while sleeping or calling the LLM.
- The hold confirms ownership before the invocation starts and cancels it when any execution is lost or no renewal succeeds `LEASE_STOP_MARGIN` before expiry. Deadlines count from before the renewal I/O and advance only when every execution renewed.
- Call `hold.confirm()` after the LLM returns, before persisting or delivering the reply. On lease loss, fail the still-owned rows with `LEASE_LOST_ERROR`. External cancellation wins and leaves the rows to lease recovery.
- Every invocation, ticked or woken, runs inside `hold.within_budget(TRIGGER_RUN_BUDGET_SECONDS)`. When the budget runs out while the leases are still valid, the hold fires through `_fire`, the invocation stops at that cancellation or its next guarded checkpoint (`ensure_held` raises `ExecutionRunTimeoutError`, a subclass of the lease error), and `hold.settle` fails the still-owned rows with `RUN_TIMEOUT_ERROR` while the heartbeat still renews. Never time a run out by letting its lease lapse: that is misfiled as lease loss. Lease loss and external cancellation win over a spent budget. The slot still comes back only from the done callback, so an invocation that ignores the cancellation keeps it until its task ends.
- Pass `hold.ensure_held` as `side_effect_guard` to `call_llm` and as `guard` to the delivery helpers, and call it right before each invoker write and push. It raises `ExecutionLeaseLostError` once the monotonic or the wall-clock deadline has passed (a suspended host stops the monotonic clock while the database lease keeps expiring). Re-raise `ExecutionLeaseLostError` before any broad `except`.
- Ticked and woken invocations start in an empty context through `trigger_daemon._start_invocation`; never let them inherit a caller's connection, tool context, or trace.
- Side effects are at least once, not exactly once. A stalled owner stops at its next guarded model round, tool call, write, or push, but work it already admitted (a running tool, thread work, a sent request) is not undone, clock skew larger than `LEASE_STOP_MARGIN` can still overlap the new owner, and work that crashes before its terminal write goes to lease recovery.
- Count `fire_count` once on first start inside the claim transaction, before invocation.
- `agent_triggers.self_disabled` records that a trigger turned itself off through `once` or `max_fires`. Only the fire-accounting update (`record_first_starts`) sets it, on the enabled-to-disabled transition. `AgentTriggerDAO.update` clears it whenever `is_enabled` is written, and the tenant/creator bulk disables clear it. Do not expose it in API responses or trigger config.
- Reclaim expired work when its trigger is enabled or `self_disabled`; fail expired work for every other disabled trigger. Claims run every tick.
- Reload trigger/agent rows via DAOs after a long LLM call; do not hold a stale `connection_ctx` across the invoke.
- Poll triggers use the shared core public-destination policy and pinned HTTP client; preserve this SSRF boundary and the existing no-redirect behavior.
- `on_message` matching must continue excluding internal trigger reflection sessions to avoid loops.

## Event Identity

- Poll state lives in trigger config JSON (no columns): `_last_value` baseline, monotonic `_poll_seq` (absent = 0), and `_poll_checked_at` last claim time. `_poll_observed` is in-memory only, set by `evaluate_trigger` for `enqueue_due_trigger`; never persist it.
- A poll change enqueues, then `agent_trigger_dao.advance_poll_baseline(expected_seq=...)` in the same `connection_ctx` transaction, after `try_enqueue`. Zero rows matched → `PollBaselineLostError` rolls the execution back; the loser never adopts its observation. Enqueue failure leaves the baseline, so the next poll re-sees the change.
- First poll and non-entering `fire_on=match` values only advance the baseline (still conditional, never an execution). Match fires each time the value enters `match_value`.
- Keys: poll `poll:{trigger}:{_poll_seq + 1}` (A-B-A-B → three runs); `on_message` `on_message:{trigger}:{_matched_message_id}`. Never hash values or message text.
- Never write internal underscore keys through `BaseDAO.update` (whole-config replace rolls the baseline back). User edits go through `merge_user_config` (SQL-side merge; `url`/`json_path` change drops `_last_value` and `_poll_checked_at` and bumps `_poll_seq`). The agent-facing trigger update tool still replaces config wholesale.
- `from_agent_name` resolves only agents in the trigger agent's tenant.
- A2A wake depth, TTL, and dedup guards live in `trigger_daemon.py`, not this package.
- Webhook dedup depends on unique `(trigger_id, idempotency_key)` semantics. `enqueue_webhook_execution` picks the key from the trigger's own config: a trigger with a `secret` dedups on `signed:` + sha256(trigger id + body) alone, ignoring every delivery header (a replaying caller controls them, the signature covers only the body); an unsigned trigger uses the first of `x-idempotency-key`, `x-github-delivery`, `x-request-id`, `x-event-id`, else the body hash.
