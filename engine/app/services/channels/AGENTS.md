# app/services/channels

Shared package for **chat / IM channel** integrations. Prefer this package for new connectors and for shared helpers when streamlining legacy modules.

## Status

This table covers transport-backed chat/IM channels only. `types.py` also registers `atlassian` and `agentbay` as `skill_only`, with `supports_inbound=False` and `supports_proactive=False`; they are intentionally omitted from the transport rows. Every provider's native inbound event is accepted durably through `submissions.py`; provider modules only parse, authenticate and enrich.

## Layout

| File | Role |
|------|------|
| `types.py` | Canonical `channel_type` registry (`ChannelKind` wraps `core/domain/channels.py` `ChannelType`), aliases, outbound keys |
| `config.py` | Shared channel_config upsert/get/delete + creator checks |
| `inbound.py` | Sender resolution, channel session, persist and reply-turn helpers; accepts through `submissions` |
| `submissions.py` | Durable native-event acceptance. One transaction: fresh authorization, receipt reserve/replay, sender quota, transcript, gateway row and reply intent. `claim_channel_event` is the advisory in-flight claim a webhook holds while it fetches media (see Native event acceptance) |
| `outbound.py`, `outbound_*.py` | Deliver a completed gateway result to the originating IM thread after native engine settlement or the independent `/gateway/report` API; `outbound_plan` (configured outbound, chunking, `build_plan`), `outbound_identity` (preflight), `outbound_transport` / `outbound_enterprise` (chunk send, ack) and `outbound_errors` (delivery errors, retry times) |
| `llm_bridge.py` | `_load_agent_and_model` plus engine LLM helpers for trigger/heartbeat only |
| `dedup.py` | Process-local plus fail-open Redis hints (`*_shared` adds SET NX). **Not authoritative**: never decides acceptance, replay or conflict |
| `redact.py` | Redact secrets for `ChannelConfigOut` API responses |
| `stream_source.py`, `stream_reconcile.py` | Connector authority of a Feishu, DingTalk, WeCom or Discord stream: `desired_stream_source` (never raises; None for unconfigured, non-stream-mode or credential-less rows) and `check_stream_source` agree. `StreamReconciler` is the one diff each manager's `reconcile_clients` runs: read the configured rows (the only read that fails a pass), start missing, finished or changed clients, stop revoked ones, never restart an unchanged source, and back off per agent (30 s toward 600 s) so one agent's failure never fails the pass |
| `media_limits.py` | Shared inbound attachment contract: web chat's 10 MiB image / 50 MiB file cap by extension, a 50 MiB per-event `MediaBudget` charging kept and aborted reads, and `read_capped` (bounded decoding, stops at the first decoded chunk past the limit; `Content-Length` is only an early reject). Slack, Telegram and WhatsApp Cloud answer after their downloads, so they build `MediaBudget.for_acknowledgement()`, which adds a wall-clock deadline of `CHANNEL_MEDIA_ACK_BUDGET_SECONDS` on an injectable clock: `limit_for` refuses a new file once it passes, `read_capped(response, limit, budget)` abandons the transfer at the next chunk, and `budget.window()` around the request cuts off a host that sends nothing. `budget.check()` before each `store_agent_upload` refuses to start a store once the deadline has passed; a store is never wrapped in `window()`, because storage finishes a write a worker thread has started before a cancellation is delivered and the file would land with its result discarded. Each raises `MediaDeadlineError`, which the provider turns into one `deadline_note` per file not fetched or not stored while still accepting the event; no other provider builds a deadline. Provider limits may be lower: `telegram_media.py` caps document/video/photo downloads at 20 MiB. Oversize raises `MediaTooLargeError`: skip the file with a transcript note and still accept the event. Do not turn timeouts, 5xx or `StorageQuotaError` into oversize notes. `limit_attachments` applies `CHANNEL_MEDIA_MAX_ATTACHMENTS` (1..10) to the provider-ordered eligible descriptors before any lookup, token, download, decryption or write (oversized ones keep their slot) and `skipped_attachments_note` is the one overflow notice; the native `ChannelEvent.media_ids` keep every original ID |

## Provider access tokens

- Google Chat (`google_chat._service_account_access_token`) and Teams (`api/teams._get_teams_access_token`, client credentials and managed identity) mint through `im_token_cache.get_or_mint_im_token`: one exchange per account per expiry window across workers, cached until the reported lifetime less the shared skew. Google signs its RS256 assertion in a worker thread and checks `token_uri` before any signing. The Azure credential is closed on success, error and cancellation. A refused exchange (non-2xx or no token) reaches only the callers waiting on it and is never cached; Redis errors fall open to a direct mint. A token exchange never logs or raises a token, an assertion or the provider's error text.
- A provider 401 drops the rejected token with `drop_rejected_im_token` (compare-and-delete) and retries once with a fresh one: `google_chat.post_chat_message` (outbound transport and proactive send, same `requestId`), Google media download (then its existing 422) and `api/teams._send_activity_renewing_token` / `outbound_enterprise` for Teams. Do not add a module-level token dict or derive a synthetic agent id for a cache key.

## Native event acceptance

- `ChannelEvent.fingerprint()` is a `v1:` SHA-256 over sender, conversation, group flag, kind, text, media and provider account/timestamp. Same `(config, provider, event_key)` with the same agent, tenant and fingerprint is a replay; any difference raises `ChannelEventConflictError`. Do not weaken either side.
- A webhook that downloads before it answers (Slack for every event, Telegram and WhatsApp Cloud for media events) first takes `submissions.claim_channel_event(event)`: Redis `SET NX` on the cache pool keyed by a hash of the receipt identity (config, provider, event key), living `CHANNEL_MEDIA_ACK_BUDGET_SECONDS` + `CLAIM_GRACE_SECONDS`, released by token compare-and-delete when the delivery ends however it ends. A delivery that finds it held raises `ChannelEventInFlightError` before any replay check, download or store: 503, `Retry-After` (the claim's lifetime) and `detail.code` `channel_event_in_flight`. Never acknowledge it with a 2xx: the provider reads that as the event delivered, so a first delivery that then fails would lose the event. The provider redelivers after the first has settled, and the redelivery is answered by the receipt (a replay, acknowledged) or, if the first failed and released its claim, processed in full. Slack redelivers a non-2xx or slow (>3 s) event up to three times (`X-Slack-Retry-Num` 1 to 3, about immediately, 1 minute and 5 minutes); the third (`accept_slack_event(final_retry=True)`, `claim_channel_event(final_delivery=True)`) ignores a held claim and proceeds, because nothing follows it, so the receipt reservation dedupes it at the cost of at most one repeated download. Telegram repeats a non-2xx webhook request and WhatsApp Cloud retries a non-200 with decreasing frequency for up to 7 days; a WhatsApp batch processes its other messages as before and then answers the whole delivery with the 503 when any message found its claim held. A claim left by a dead process expires, and an unavailable store (Redis down, breaker open, pool busy) lets the delivery proceed as before. It is advisory like `dedup.py`: the receipt reservation in `accept_channel_event` stays the only durable dedupe, and the replay check runs under the claim.
- The media budget stops new fetches and new stores. Once the deadline passes no file is requested and no store starts (each one and every later file gets its `deadline_note`), a fetch in progress is abandoned, but a store that started before the deadline runs to completion and is attached normally. The overrun is therefore at most one store, limited by the storage client's timeouts (S3: `connect_timeout` 5 s and `read_timeout` 30 s per attempt in `storage_runtime/s3_connection.py`; the local backend is a disk write). The replay check before the fetches and the acceptance transaction (`accept_channel_event`) after them stay outside the budget, which is what `CLAIM_GRACE_SECONDS` covers; do not move acceptance under the budget, and do not cancel a store at the deadline.
- `is_channel_event_replay` is a read-only precheck: it authorizes first, then compares the stored receipt without reserving. Authorization re-reads the config, agent, bound sender (`resolve_bound_sender`), `load_user_principal(fresh=True)`, active tenant and `manage`/`use` access every time.
- `sender_links.py` handles private Telegram/Zalo `/start` and `/link` commands. A provider account or contact is not membership authority: resolve the explicit sender binding and freshly check same-tenant membership, active company and `manage`/`use` access through `authorize_member`.
- A WhatsApp config with `extra_config.mode == "personal_qr"` is refused for ordinary events (403); only an event carrying a matching `personal_source` may use it.
- A direct message's transcript is the linked sender's canonical session: `binding.bind_channel_conversation` resolves it with `ensure_canonical_session`, an unlinked sender is rejected, and a group conversation is its own transcript (the reply session). `persist_channel_user_message` publishes the IM user message to the owner only. Personal bursts use the creator's canonical session as `transcript_session_id`.
- `submissions._ensure_owner_transcript` ensures that Personal transcript before the acceptance transaction, because `personal_owner` holds `FOR UPDATE` on tenant, creator and agent until commit and a first canonical insert under those locks can deadlock. Linked non-Personal senders ensure inside the transaction, before `lock_for_agent` of the transcript. Lock order: [shared runtime](../../../docs/shared-openclaw-runtime.md#lock-order).

## Personal WhatsApp (QR)

Fenced by `config_id`, `auth_epoch`, `generation`, lease `claim_token` and `account_id`; any mismatch revokes the source. Bridge package: `engine/connectors/whatsapp` (`connectors/whatsapp/AGENTS.md`).

- `whatsapp_personal_control.py` owns the creator-only `status`, `start` (QR, relink) and `disconnect`; `whatsapp_personal_access.py` `personal_owner` re-checks creator, fresh principal and active tenant under share or exclusive locks.
- `whatsapp_personal_supervisor.py` (connector-role loop, readiness progress budget) polls `candidates()`, beats after each finished pass (a failed pass backs off without a beat; bridge children never beat), `claim`s one config and runs `whatsapp_personal_child.py`, which spawns the Node bridge with only `PATH` in its environment and a per-run token. A child that fails unclassified (stored credentials untouched) leaves `running` at once and records a per-config cooldown deadline: `ReconnectBackoff` jitter from 30 s toward a 300 s cap, restarted only after a child stayed up 120 s on the injectable monotonic clock; cooldown and escalation state is pruned to the current candidates (and running children) after each finished pass. Fleet pacing (shared with the Zalo supervisor): `candidates()` is one joined read (connection rows left-joined to `channel_configs.extra_config`, retry gate parsed once per row by `startable_since`) returning the due set longest waiting first (the later of `updated_at` and `retry_at`; `reaped` and `start` stamp `updated_at`); each pass claims the connections not running or cooling down in that order inside the poll loop and starts at most `min(WHATSAPP_PERSONAL_MAX_RUNNING_CHILDREN - running, WHATSAPP_PERSONAL_MAX_STARTS_PER_POLL)` children (`running` is this process's); a declined claim (`None`) spends no pace and a claim that raises takes the cooldown path; the pass still beats. The ceiling itself is fleet-wide: `claim` locks its connection `FOR UPDATE SKIP LOCKED` (a row held elsewhere is declined without waiting), re-checks the retry gate, then `dao/personal_bridge_fleet.admit` takes the transaction-scoped advisory lock `personal_bridge_fleet:whatsapp` (Zalo: `personal_bridge_fleet:zalo`; no other engine advisory key shares the prefix), counts live leases (`claim_token` set and `lease_until` ahead; partial index `ix_whatsapp_personal_live_leases`) and raises `FleetFullError` at the ceiling, so any number of processes never exceed it and a dead process's lease stops counting after 30 s. The supervisor ends that poll's claims on `FleetFullError` and logs `fleet_ceiling_reached` once per episode with the fleet-wide count. Each claim runs under `anyio.fail_after(_CLAIM_TIMEOUT_SECONDS)` (10 s; the cancelled transaction rolls back and returns its connection): a timeout takes the cooldown path like a claim that raises and, because a hung claim usually has a shared cause (a stuck fleet-lock holder, the database), also ends that poll's claims with a `claim_abandoned` warning naming the config id and the deferred count: one poll spends at most one claim budget, the pass still beats and the next poll starts with the connections behind it (any other claim error only skips its connection). No process-local counter and no Redis stand in for the database count. `spawn_child` appends `--worker-heap-mb=<WHATSAPP_PERSONAL_WORKER_HEAP_MB>` to the command (the environment stays `PATH` only); a bridge whose worker runs out of memory exits non-zero, which `run_child` treats like any non-zero exit. Frames are the strict `extra="forbid"` models in `whatsapp_personal_protocol.py`. Auth and QR values are sealed by `whatsapp_personal_crypto.py` (AES-GCM, AAD bound to config, epoch, category, key id); a store or decrypt failure fails the connection as `auth_store_failed`. Transient causes (a bridge `transport_failed` close, a non-zero exit, `OSError`/broken pipe, a malformed frame) on a paired connection keep credentials, desire and generation and move it to `reconnecting`; `dao/whatsapp_personal_runtime_dao.py` charges the budget in `extra_config.whatsapp_runtime` (5, 15, 30, 60, 120 s), `candidates()`/`claim()` skip a future `retry_at` and re-check it under the row lock, an exhausted budget pauses with credentials kept, and the owner's start or relink clears it. The budget refills only after `PersonalChild` sees the link stay up 120 s (injectable clock), never on socket open. Pending sends survive a retry. Unpaired attempts, lost owner authorization (told apart because `personal_owner` raises, although the code is also `transport_failed`), account conflicts, ambiguous identity and auth-store failures keep their terminal path.
- `whatsapp_personal_events.py` handles bridge frames, binds the account identity (ambiguous identity fails), decides a transient retry in `interrupted` and otherwise calls `revoke_current_claim`; diagnostics log typed summaries (`error_summary`, stages, drop reasons), not message text or auth values.
- `whatsapp_personal_intake.py` re-validates the live connection and unexpired lease, rejects assistant echoes by looking up the `whatsapp_personal_sends` message id, and accepts only the owner's self-chat messages (`from_me`, no participant, `remote_jid` is the linked account) stamped after activation. Its event key is `personal:{auth_epoch}:{message_id}`.
- `whatsapp_personal_journal.py` is the durable send journal (`pending`, `dispatch_started`, `accepted`, `rejected`, `uncertain`, `cancelled`). `enqueue` is idempotent on `command_id`, and surfaces `rejected`, `uncertain` or `cancelled` as `PersonalSendTerminalError` and `pending` or `dispatch_started` as `PersonalSendPendingError`; `authorize_dispatch` claims the oldest pending row under the lease with no provider I/O in the transaction.
- `personal_burst_*` batch fresh originals: `admission` runs capacity, then quota, then durable acceptance; `gateway` writes the pending burst anchor and the static "not queued" source, `notice` records terminal rejections with at most one notice per scope cooldown, `outcome` holds the typed accepted/replayed/rejected result and `limits` projects settings. The worker loop `services/openclaw_dispatch_reconciler.py` recovers pending ready heads through the same native drain and `claim_ready_shared` authority; PostgreSQL is the readiness authority. Unready heads and delivered turns block younger work in the same human lane; uncertain execution is never timeout-requeued.

## Personal Zalo (QR)

- `zalo_personal_supervisor.py` claims candidate configs and owns `zalo_personal_child.py` bridge processes from `engine/connectors/zalo`. It runs under the connector role; only successful candidate passes beat readiness. A child that fails unclassified follows the same per-config jittered cooldown as WhatsApp (30 s toward 300 s, restarted after a 120 s healthy run): it leaves `running` at once and the supervisor skips the config until its deadline, so no sleeping child task is left behind. Fleet pacing mirrors WhatsApp with the `ZALO_PERSONAL_*` settings (running ceiling, starts per poll, `--worker-heap-mb` at spawn; `claim` runs in the poll loop and only winning claims spend pace, which matters because `claim` declines a stopped agent forever; the running ceiling is fleet-wide through the same `personal_bridge_fleet` admission under the `personal_bridge_fleet:zalo` lock, `claim` skips a connection row locked elsewhere, and each claim has the same 10 s budget, cooldown path and end-of-poll on timeout); its `candidates()` is the same one joined read over the `pending`/`reconnecting` rows. A worker out of memory makes the bridge close with `transport_failed`, which `interrupted` charges to the durable retry budget.
- `zalo_personal_intake.py` handles link commands, then requires a bound private peer for work. Reject `from_me`, self-chat, non-private threads and messages before activation or over 60 seconds ahead. Intake and linking require a `zalo_source` fenced by config, auth epoch, generation, claim token and account; `zalo_personal_source.py` also rejects journaled assistant echoes.
- `zalo_personal_journal.py` journals text/file sends by route and `command_id`; revoked routes and unbound reply peers fail closed. `uncertain` is terminal, never automatically retried.
- Setup, recovery and media policy: [channel operations](../../../docs/channels.md#telegram-bot-and-zalo-personal). Bridge contract: `engine/connectors/zalo/AGENTS.md`.

## Adding a channel

1. Add `ChannelKind` to `types.py`, `ChannelType` in `core/domain/channels.py`, and extend Postgres `channel_type_enum` in the fresh-only `scripts/schema_baseline.sql`.
2. Implement API under `app/api/<channel>.py` (CRUD + webhook/stream entry). Prefer `channels.config` + `channels.inbound`; build a `ChannelEvent` and call `accept_channel_event`.
3. Register router in `app/main.py`.
4. If proactive send is supported, add sender under `agent_tool_exec/channel_provider_*` and register in `channel_messaging` via the outbound registry.
5. Ensure `channel_user_service` can resolve identities for the type.

## Do not

- Invent a second channel type string for the same product (use aliases in `types.py`).
- Treat Redis dedup or a process-local hit as proof of acceptance or replay.
- Put SSO/login OAuth in channel adapters. Provider directory admin sync is retired; Google Chat authentication and user gogcli OAuth remain separate live contracts.
- Grow `agent_tools.py` with channel branches; use `agent_tool_exec` + this package.
- Move LLM orchestration back into `api/feishu.py`. New IM callers should enqueue via `inbound.generate_channel_reply` / `run_text_turn`; native terminal settlement persists replies and the durable report relay sends the accepted IM intent. The independent `/gateway/report` API remains available.
