# Runtime Lifecycle

Owns per-lifespan process resources, background work and readiness. `app/main.py` imports `lifespan` here; HTTP assembly stays in `main.py`, schema initialization in `app/scripts/bootstrap_db.py`.

## Code Map

| File / symbol | Responsibility |
|---|---|
| `lifecycle.py`: `Runtime`, `lifespan` | Role-gated startup, attempted-resource bookkeeping, ordered/shielded shutdown; fresh state each lifespan. |
| `tasks.py`: `OwnedTasks`, `LoopProgress`, `EventTasks`, `TaskAdmission`, `cancel_tasks` | Explicit task ownership, required-task evidence and opt-in progress budgets, SDK callback and producer admission/drain. |
| `readiness.py`: `Readiness`, `router` | `/api/ready`, bounded existing-dependency probes, drain-aware eligibility. |
| `bootstrap.py`: `bootstrap` | Ordered seed boundaries; no schema DDL. |
| `connectors.py`: `WeChatRuntime` | Finite initial reconciliation followed by a required ongoing loop. |
| `proxy.py`: `ShadowsocksProxy` | Connector-owned ss-local process, secret temp config and reversible `DISCORD_PROXY`. |
| `diagnostics.py` | Warn-only bwrap probe; default-secret warnings stay in `lifecycle.py`. |

## Roles And Startup

- `../process_roles.py` is dependency-free: comma-split, strip, lowercase, deduplicate; blank means `all`. Reject unknown roles even alongside `all`; then `all` dominates. Valid roles: `all`, `bootstrap`, `api`, `worker`, `connector`.
- `../../entrypoint.sh` runs this normalizer before permissions/resource work and its case-sensitive role predicate. `Bootstrap` runs schema bootstrap. Only `all`/`bootstrap` invoke `app.scripts.bootstrap_db`; `ALLOW_MIGRATION_FAILURE=true` is explicit continuation after failure, not an Alembic switch.
- `lifespan` validates roles before allocating `Runtime`, exposes `app.state.readiness`, and owns cleanup even after partial startup. Routers remain mounted for every role; bootstrap-only processes never become ready.
- Startup reopens route/schedule and trigger/heartbeat/inbox-wake admission, configures logging/interception, runs warn-only diagnostics, then opens the pool for every valid role. Bootstrap runs only when enabled; API/worker/connector roles then initialize Redis.
- API starts the realtime subscriber. Worker starts required loops: `trigger_daemon`, independent `heartbeat`, `agent_setup`, durable start recovery (`agent_start_reconciler`), `cache-invalidation-recovery`, `auth_email`, `broadcast_fanout`, `broadcast_email`, `chat_history_retention`, `operational_log_retention`, organization admission credential email (`organization_admission_email`), `web_search_export`, `agent_scheduler`, `gateway_report_relay`, OpenClaw upgrade worker (`openclaw_update`), pending native dispatch recovery (`openclaw_dispatch`, `openclaw_dispatch_reconciler_loop`), including due Personal WhatsApp bursts, `openclaw_delayed_replies` and `task_lease_recovery`. Dispatch scans keyset pages of 50 with a one-second interval and never replays delivered turns. Connector starts the Personal WhatsApp supervisor (`whatsapp_personal` loop), the `ss-local-proxy` and per-manager finite setup tasks, then the `transfer_cleanup` loop. Wire these in `lifecycle.py`, not the task-ownership primitives in `tasks.py`. Set `initialized` last; this alone does not mean setup tasks finished or the process is ready.
- Seed order: system orgs, platform admin, built-in tools/orphan MCP cleanup, optional Atlassian config/tools, role templates, skills and existing-agent push, default/OKR agents. Tavily payloads are bundled in the OpenClaw guest image, not seeded by engine. All system-org and PA seed failures propagate; optional block failures warn and allow later blocks.

## Owned Tasks And Readiness

- Worker also owns `task_lease_recovery`: every 30 seconds it returns expired task claims to pending with a log, without rerunning them. Task runs renew their 120-second leases every 30 seconds from whichever process scheduled them; API and connector roles never scan or reset task claims at startup.

- Track only owned tasks; never cancel a global `asyncio.all_tasks()` set. Cancel unfinished tasks and await them with `gather(return_exceptions=True)`; log non-cancellation failures.
- `OwnedTasks.start` distinguishes optional, finite `setup`, and ongoing `loop`. Required setup is ready only after successful completion; a required loop is ready only while running. Normal loop return, failure or cancellation invalidates readiness. Retain required evidence after done-task removal.
- Every required loop has a progress budget (`OwnedTasks.start(..., progress_budget_seconds=)`, loops only); the loop calls `loop_progress().beat()` after each finished pass, and readiness also fails once the last beat (task start counts) is older than the budget on `OwnedTasks`' injectable monotonic clock. Each loop's module defines `PROGRESS_BUDGET_SECONDS`, 300 seconds except `broadcast_fanout` (90), and `lifecycle.py` registers it for every worker loop listed under Roles And Startup plus `whatsapp_personal` and `transfer_cleanup`; `connectors.py` registers `wechat-reconcile`. Staleness never cancels or restarts a loop. A beat means the loop's own pass finished: child tasks (the heartbeat's stopped-container reconciliation, gateway-report deliveries, Personal WhatsApp bridges, WeChat pollers) never beat, and a pass retried in place after an error never beats. `loop_progress().exempt()` excludes work that has its own duration contract: time inside is not staleness and the window restarts on exit; `restart_on_error=False` leaves an exception without that restart. The trigger daemon beats only after a tick returns without raising; evaluations run in scanner tasks under their own deadline, so a tick stuck on an inline DAO await is what goes stale. Email workers retry only DB errors from `claim_batch`/`purge_settled` in place with capped backoff (no beat; a purge failure does not block claiming) and keep a batch timeout or error fatal. The upgrade worker reacquires Docker with capped backoff via `agent_manager.reacquire_docker_client()` (shared `docker_client`), beats while idle without Docker, stops beating while runs are active (or unreadable), and wraps `executor.process` in `loop_progress().exempt()`: no deadline, never cancelled, time inside is not staleness.
- Scanner budgets are observation windows above their 10-second start, 30-second schedule and one-second native-recovery cadences, allowing the default 30-second pool checkout/statement limits and bounded pages (native evidence reads have a two-second query bound). Start recovery beats after an empty selection or a completed operation and exempts only `start_container`: its Docker preparation and aggregate admission fence have no total deadline, and cancellation drains it under the workspace fence. Selection, eligibility/recovery, reservation, publication and cancelled cleanup remain observable. Scheduler beats only after both manual and periodic claim/launch/release passes succeed, or when execution capacity is exhausted; internally caught errors return failure. Native recovery beats after pending and delivered pages both complete, including an empty scan; in-memory cursors advance only after their page completes, so later pages cannot hide a repeated page failure. Unreadable guest evidence is a failed scan, never permission to resubmit delivered input. These budgets impose no operation deadlines and do not change claims or durable intent.
- Other worker beat points. `heartbeat`: after a tick's candidate selection and claims finish (an idle tick counts). Stopped-container reconciliation is its single-flight child task: started when none is in flight, never awaited by a tick, never exempt, so a hung run delays only the next reconciliation; loop cancellation cancels and awaits it. `agent_setup`: after each completed pass, idle included; `run_agent_setup` and `run_agent_setup_mcp` run in `exempt(restart_on_error=False)`, which covers the unbounded `setup_workspace_lock` wait, and a failed claim or an expected worker IO error retried in place never beats. `task_lease_recovery`: after a successful scan. `openclaw_delayed_replies`: after a scan with no PostgreSQL error (one caught per binding counts). `web_search_export`: after each drain or reclaim, a failed S3 PUT included; hourly retention runs after the beat. `gateway_report_relay`: after each claim attempt. `cache-invalidation-recovery`: after a complete replay pass. `auth_email`: after each processed batch. `broadcast_fanout`: after each completed batch. `chat_history_retention`: after every completed purge batch, an empty one and `CHAT_HISTORY_RETENTION_DAYS=0` included. Those four retry database errors in place with capped backoff (1 to 30 seconds) and no beat. `operational_log_retention` (`app/services/operational_log_retention_worker.py`): one pass purges one batch of at most 5000 rows from each enabled table (`agent_activity_logs` older than `ACTIVITY_LOG_RETENTION_DAYS`; completed or failed `trigger_executions` finished before `TRIGGER_EXECUTION_RETENTION_DAYS`, which rejects 1 to 6 at settings load), each in its own transaction with `FOR UPDATE SKIP LOCKED`. It beats only after a pass in which no purge raised, an empty pass and both settings at 0 (no database call) included. A database error on either table retries the whole pass in place with capped backoff (1 to 30 seconds) and no beat, and the other table is still attempted. It sleeps 60 seconds only when every batch came back short; a full batch loops again at once.
- `EventTasks` tracks admitted SDK callbacks; closing rejects new callbacks with `CancelledError`, then cancels/awaits existing callbacks. Do not let callbacks outlive their manager's ownership.
- Readiness requires initialized, not draining, an API/worker/connector role, satisfied required tasks, and API realtime subscription readiness when applicable.
- Probe existing pool and Redis concurrently with separate two-second bounds; probes must not initialize resources. Skip probes while ineligible and recheck eligibility after them to catch draining/subscription races.
- `/api/ready` returns 200 `{"status":"ready"}` or 503 `{"status":"not_ready"}`; never leak driver/credential details. `/api/health` remains the independent pool-only check.

## Shutdown And Connectors

- Mark draining and synchronously close trigger/heartbeat/inbox-wake admission before teardown so readiness fails immediately and producers refuse new work. Stop route background work, owned wrappers, schedule executions and connector managers, then drain trigger invocations, heartbeats and native per-agent drains (`openclaw_routing` inbox-wake admission) before proxy, realtime subscriber, pool, Redis, LLM clients, outbound and Tavily HTTP pools, and logging. Each producer drain waits within its grace period, then cancels and awaits only its owned work. Native cancellation joins and reaps the local Docker CLI before payload cleanup or guest exclusion release, even under repeated cancellation; it does not prove cancellation of a detached Gateway run. Use attempted-resource flags to clean partial acquisition.
- Shield the cleanup task with both AnyIO cancellation shielding and `asyncio.shield`; repeated task cancellation must not interrupt cleanup. Await completion, preserve an original failure, otherwise re-raise cancellation. Each cleanup boundary logs failures/cancellation and continues.
- Feishu, DingTalk, WeCom, WeChat and Discord setup wrappers are finite `setup` requirements; manager-owned SDK loops are stopped through `stop_all`. A successful setup return must not be classified as a dead required loop.
- WeChat first awaits `reconcile_clients`, then owns `start_all` as required loop `wechat-reconcile`. Keep that ongoing-loop requirement separate from finite setup. The first `reconcile_clients` is not retried: its failure fails that setup task and readiness, and the loop is never started. Inside the loop, `reconcile_clients` errors retry in place with capped backoff (1 to 30 seconds) and no beat; a successful pass beats, and pollers never beat.
- `transfer_cleanup` first awaits every required finite setup task inside `loop_progress().exempt(restart_on_error=False)`, then runs `start_transfer_cleanup_reconciler()` (a one-second polling loop). It beats only when `reconcile_transfer_cleanup()` returns `True`; that returns `False` only when the pending queue could not be read, never beats itself, and its other callers ignore the result. `whatsapp_personal` (`personal_supervisor`) starts immediately, beats after each finished `candidates()` pass (a failed pass backs off without a beat), and spawns the Node bridge per claimed connection; bridge children never beat. Its contract is `../services/channels/AGENTS.md`.
- No connector startup from request handlers or before pool initialization. Existing per-client post-save startup is governed by the engine-wide exception.

## Proxy Resource Boundary

- Connector proxy setup is optional: missing ss-local skips; unusable nodes warn and skip. Nodes come from `SS_CONFIG_FILE` (default `/data/ss-nodes.json`), otherwise `SS_SERVER`/`SS_PASSWORD` settings when the file is absent.
- Keep credentials in the temporary config passed as `ss-local -c <path>`. Shield subprocess creation so cancellation still records the process for cleanup; publish `DISCORD_PROXY=socks5h://127.0.0.1:1080` only after the child survives startup. Save the previous env value before publishing.
- Failed/cancelled unpublished attempts shield cleanup, stop the child and unlink config. Shutdown terminates/waits five seconds, then kills/waits five seconds if needed; finally unlink config, clear ownership and restore the previous `DISCORD_PROXY` or remove it if originally absent.
- Successful finite proxy setup is not an ongoing subprocess-liveness probe. Keep connector proxy env separate from the sandbox guest `SANDBOX_*_PROXY` trust boundary.
