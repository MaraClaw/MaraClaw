# Runtime Lifecycle

Owns per-lifespan process resources, background work and readiness. `app/main.py` imports `lifespan` here; HTTP assembly stays in `main.py`, schema initialization in `app/scripts/bootstrap_db.py`.

## Code Map

| File / symbol | Responsibility |
|---|---|
| `lifecycle.py`: `Runtime`, `lifespan` | Role-gated startup, attempted-resource bookkeeping, ordered/shielded shutdown; fresh state each lifespan. |
| `tasks.py`: `OwnedTasks`, `RestartPolicy`, `LoopProgress`, `EventTasks`, `TaskAdmission`, `cancel_tasks`, `capped_backoff`, `jittered_backoff`, `ReconnectBackoff` | Explicit task ownership, required-task evidence and opt-in progress budgets, SDK callback and producer admission/drain. Deterministic worker backoff, plus jittered connector reconnect delays that reset only after a healthy run. |
| `readiness.py`: `Readiness`, `router` | `/api/ready`, bounded existing-dependency probes, drain-aware eligibility; `/api/live`, the container liveness route (`Readiness.alive`). |
| `bootstrap.py`: `bootstrap` | Ordered seed boundaries; no schema DDL. |
| `connectors.py`: `ReconcileRuntime`, `ConnectorManager` | The one adapter for every IM manager (`feishu`, `dingtalk`, `wecom`, `wechat`, `discord`): a finite first `reconcile_clients` pass, then the required `<provider>-reconcile` loop. |
| `proxy.py`: `ShadowsocksProxy` | Connector-owned ss-local process, secret temp config and reversible `DISCORD_PROXY`. |
| `diagnostics.py` | Warn-only bwrap probe; default-secret warnings stay in `lifecycle.py`. |

## Roles And Startup

- `../process_roles.py` is dependency-free: comma-split, strip, lowercase, deduplicate; blank means `all`. Reject unknown roles even alongside `all`; then `all` dominates. Valid roles: `all`, `bootstrap`, `api`, `worker`, `connector`.
- `../../entrypoint.sh` runs this normalizer before permissions/resource work and its case-sensitive role predicate. `Bootstrap` runs schema bootstrap. Only `all`/`bootstrap` invoke `app.scripts.bootstrap_db`; `ALLOW_MIGRATION_FAILURE=true` is explicit continuation after failure, not an Alembic switch.
- `lifespan` validates roles before allocating `Runtime`, exposes `app.state.readiness`, and owns cleanup even after partial startup. Routers remain mounted for every role; bootstrap-only processes never become ready.
- Startup reopens route/schedule and trigger/heartbeat/inbox-wake admission, configures logging/interception, runs warn-only diagnostics, then opens the pool for every valid role. Bootstrap runs only when enabled; API/worker/connector roles then initialize Redis.
- API starts the realtime subscriber. Worker starts required loops: `trigger_daemon`, independent `heartbeat`, `agent_setup`, durable start recovery (`agent_start_reconciler`), `cache-invalidation-recovery`, `auth_email`, `broadcast_fanout`, `broadcast_email`, `chat_history_retention`, `agent_workspace_quota`, `workspace_mirror`, `agent_resource_pressure`, `operational_log_retention`, `capacity_renewal`, organization admission credential email (`organization_admission_email`), `web_search_export`, `agent_scheduler`, `gateway_report_relay`, OpenClaw upgrade worker (`openclaw_update`), pending native dispatch recovery (`openclaw_dispatch`, `openclaw_dispatch_reconciler_loop`), including due Personal WhatsApp bursts, `openclaw_delayed_replies` and `task_lease_recovery`. Dispatch scans keyset pages of 50 with a one-second interval and never replays delivered turns. Connector starts the required Personal WhatsApp and Personal Zalo supervisor loops (`whatsapp_personal`, `zalo_personal`), the `ss-local-proxy`, one finite first-pass setup task per IM manager (`feishu`, `dingtalk`, `wecom`, `wechat`, `discord`, each registering its `<provider>-reconcile` loop), then the `transfer_cleanup` loop. Wire these in `lifecycle.py`, not the task-ownership primitives in `tasks.py`. Set `initialized` last; this alone does not mean setup tasks finished or the process is ready.
- Seed order: system orgs, platform admin, built-in tools/orphan MCP cleanup, optional Atlassian config/tools, role templates, skills and existing-agent push, default/OKR agents. Tavily payloads are bundled in the OpenClaw guest image, not seeded by engine. All system-org and PA seed failures propagate; optional block failures warn and allow later blocks.

## Owned Tasks And Readiness

- Worker also owns `task_lease_recovery`: every 30 seconds it returns expired task claims to pending with a log, without rerunning them. Task runs renew their 120-second leases every 30 seconds from whichever process scheduled them; API and connector roles never scan or reset task claims at startup.

- Track only owned tasks; never cancel a global `asyncio.all_tasks()` set. Cancel unfinished tasks and join them with `shutdown_budget.join` (`asyncio.wait`, never `gather`): outside shutdown it waits for every task; inside a `Runtime.stop` step it stops at the step's deadline, logs the names of the tasks still running and returns without cancelling anything again. Log non-cancellation failures.
- `OwnedTasks.start` distinguishes optional, finite `setup`, and ongoing `loop`. Required setup is ready only after successful completion; a required loop is ready only while running. Normal loop return, failure or cancellation invalidates readiness. Retain required evidence after done-task removal.
- Every required loop has a progress budget (`OwnedTasks.start(..., progress_budget_seconds=)`, loops only); the loop calls `loop_progress().beat()` after each finished pass, and readiness also fails once the last beat (task start counts) is older than the budget on `OwnedTasks`' injectable monotonic clock. Each loop's module defines `PROGRESS_BUDGET_SECONDS`, 300 seconds except `broadcast_fanout` (90) and the `agent_workspace_quota` / `agent_resource_pressure` modules, which expose `progress_budget_seconds()` (their interval setting, `AGENT_WORKSPACE_QUOTA_INTERVAL_SECONDS` or `AGENT_RESOURCE_PRESSURE_INTERVAL_SECONDS`, plus named per-page bounds instead of a flat allowance, because both beat after every page; the bounds are listed under the other worker beat points), and `capacity_renewal` (`app/services/capacity_renewal_worker.py`: `CAPACITY_RENEWAL_INTERVAL_SECONDS`, default 3600, plus 600 seconds; a pass expires stale capacity orders and creates the month's renewals, beats after the pass, one company's failure is logged and the pass goes on, a database error retries in place with the same capped backoff and no beat), and `lifecycle.py` registers it for every worker loop listed under Roles And Startup plus `whatsapp_personal`, `zalo_personal` and `transfer_cleanup`; `connectors.py` registers `feishu-reconcile`, `dingtalk-reconcile`, `wecom-reconcile`, `wechat-reconcile` and `discord-reconcile` with its own `PROGRESS_BUDGET_SECONDS`. Staleness never cancels or restarts a loop. A beat means the loop's own pass finished: child tasks (the heartbeat's stopped-container reconciliation, gateway-report deliveries, Personal WhatsApp bridges, IM stream clients, WeChat pollers) never beat, and a pass retried in place after an error never beats. `loop_progress().exempt()` excludes work that has its own duration contract: time inside is not staleness and the window restarts on exit; `restart_on_error=False` leaves an exception without that restart. The trigger daemon beats only after a tick returns without raising; evaluations run in scanner tasks under their own deadline, so a tick stuck on an inline DAO await is what goes stale. Email workers retry DB errors from `claim_batch`/`purge_settled` in place with capped backoff (no beat; a purge failure does not block claiming). Auth email also retries transient DB settlement failures per claim; unexpected delivery errors and batch timeouts end the incarnation (the supervisor restarts it). The upgrade worker reacquires Docker with capped backoff via `agent_manager.reacquire_docker_client()` (shared `docker_client`), beats while idle without Docker, stops beating while runs are active (or unreadable), and wraps `executor.process` in `loop_progress().exempt()`: no deadline, never cancelled, time inside is not staleness.
- Scanner budgets are observation windows above their 10-second start, 30-second schedule and one-second native-recovery cadences, allowing the default 30-second pool checkout/statement limits and bounded pages (native evidence reads have a two-second query bound). Start recovery beats after an empty selection or a completed operation and exempts only `start_container`: its Docker preparation and aggregate admission fence have no total deadline, and cancellation drains it under the workspace fence. Selection, eligibility/recovery, reservation, publication and cancelled cleanup remain observable. Scheduler beats only after both manual and periodic claim/launch/release passes succeed, or when execution capacity is exhausted; internally caught errors return failure. Native recovery beats after pending and delivered pages both complete, including an empty scan; in-memory cursors advance only after their page completes, so later pages cannot hide a repeated page failure. Unreadable guest evidence is a failed scan, never permission to resubmit delivered input. These budgets impose no operation deadlines and do not change claims or durable intent.
- Other worker beat points. `heartbeat`: after a tick's candidate selection and claims finish (an idle tick counts). Stopped-container reconciliation is its single-flight child task: started when none is in flight, never awaited by a tick, never exempt, so a hung run delays only the next reconciliation; loop cancellation cancels and awaits it. `agent_setup`: after each completed pass, idle included; `run_agent_setup` and `run_agent_setup_mcp` run in `exempt(restart_on_error=False)`, which covers the unbounded `setup_workspace_lock` wait, and a failed claim or an expected worker IO error retried in place never beats. `task_lease_recovery`: after a successful scan. `openclaw_delayed_replies`: after a scan with no PostgreSQL error (one caught per binding counts). `web_search_export`: after each drain or reclaim, a failed S3 PUT included; hourly retention runs after the beat, in bounded batches with an extra beat after each full one. `gateway_report_relay`: after each claim attempt. `cache-invalidation-recovery`: after a complete replay pass. `auth_email`: after each processed batch. `broadcast_fanout`: after each completed batch. `chat_history_retention`: after every completed purge batch, an empty one and `CHAT_HISTORY_RETENTION_DAYS=0` included. Those four retry database errors in place with capped backoff (1 to 30 seconds) and no beat. `agent_workspace_quota` and `agent_resource_pressure` (`app/services/agent_workspace_quota_worker.py`, `agent_resource_pressure_worker.py`): after every completed page of non-system organization agents (50 per page, in id order), a page whose agent or sampling failure was logged included; they sleep their interval after the last page, and a database error reading a page retries in place with the same capped backoff and no beat. The longest silence is the interval sleep followed by one page, so each `progress_budget_seconds()` is the interval plus that page's named bounds. Quota: `PAGE_READ_SECONDS` (60) plus `ceil(50 / AGENT_WORKSPACE_QUOTA_CONCURRENCY)` agents at `AGENT_SECONDS` (240 = `WALK_DEADLINE_SECONDS` 120 + `LAYER_INSPECT_TIMEOUT_SECONDS` 60 + `AGENT_DATABASE_SECONDS` 60). Up to `AGENT_WORKSPACE_QUOTA_CONCURRENCY` (default 4, range 1 to 32) agents of a page are measured at once, each lane taking the next waiting agent the moment it frees, so every lane stays busy until the page runs out and the page ends within that many agents at their bound, whatever each takes: the interval plus 3180 seconds at the default concurrency, 3780 at the default 600-second interval (12060 and 12660 with one lane). A quota pass pages first the agents whose usage row asks to be measured first (a failed directory walk, or a request path that handed its re-measure over; `list_workspace_quota_priority_page`), then every other agent in id order without repeating them; the priority pages beat like any other page, an empty one included. Pressure: `ORPHAN_SWEEP_SECONDS` (60) + `PAGE_READ_SECONDS` (60) + `PAGE_DOCKER_SECONDS` (120, two `DOCKER_TIMEOUT_SECONDS`) + `PAGE_DATABASE_SECONDS` (600), so the interval plus 840 seconds, 1140 at the default 300-second interval. A page held past its budget turns the loop stale without cancelling it. The quota walk checks `WALK_DEADLINE_SECONDS` inside its own thread (`measure_directory_bytes` raises `WorkspaceMeasurementTimeoutError`, so no walk thread outlives it), and a timed-out measurement records only a failed walk on the usage row (`walk_failed_at`, through `record_walk_failure`; a row with NULL `measured_at` and zero placeholder sizes for an agent never measured): no size, pressure sample or alert, the stored sizes and `over_since` stand so it neither lifts nor creates a block, and the next pass measures that agent first. The pressure pass shares one `GuestReads` per pass: once `inspect_guests` or `guest_stats` returns `None` (a fast refusal included), later pages of that pass make neither Docker call, still close agents that have no guest and sample storage from the database, and never close an episode for a skipped reading; the next pass asks Docker again. `agent_resource_pressure` also owns the `docker events` OOM reader (`agent_resource_pressure_events.py`) as an anyio child task of the loop: it never beats and never raises, restarts its CLI child with capped backoff (1 to 60 seconds), and cancellation terminates and reaps that child, so a slow or failing reader cannot make the worker unready. `operational_log_retention` (`app/services/operational_log_retention_worker.py`): one pass runs one batch of at most 5000 rows for each enabled table, from a table-driven list, each in its own transaction with `FOR UPDATE SKIP LOCKED` (a cancelled pass leaves only whole committed batches). `agent_activity_logs` older than `ACTIVITY_LOG_RETENTION_DAYS` and completed or failed `trigger_executions` finished before `TRIGGER_EXECUTION_RETENTION_DAYS` are deleted; `content` and `result` of completed `gateway_messages` completed before `GATEWAY_MESSAGE_RETENTION_DAYS` are cleared, keeping the row and skipping any message with a delivery neither delivered nor terminal. Five more tables are opt-in: `notifications` older than `NOTIFICATION_RETENTION_DAYS`; `done` `tasks` (finished at `COALESCE(completed_at, updated_at)`, because the task tool can set done without `completed_at`) with their `task_logs` after `TASK_RETENTION_DAYS`, never a pending or doing one; `channel_event_receipts` older than `CHANNEL_EVENT_RECEIPT_RETENTION_DAYS`, which takes the receipt's media descriptors and burst outcomes with it (`ON DELETE CASCADE`); delivered or terminal `gateway_report_deliveries` after `GATEWAY_REPORT_DELIVERY_RETENTION_DAYS` (a pending delivery never, the gateway message rows stay); and `workspace_file_revisions` created before `WORKSPACE_REVISION_RETENTION_DAYS` that a newer revision of the same agent file replaced (the newest revision of each file is never deleted). Every setting defaults to 0, which keeps the rows forever and issues no SQL for that table; the trigger, gateway message and receipt windows reject 1 to 6 at settings load. It beats only after a pass in which no purge raised, an empty pass and every setting at 0 (no database call) included. A database error on any table retries the whole pass in place with capped backoff (1 to 30 seconds) and no beat, and the other tables are still attempted. It sleeps 60 seconds only when every batch came back short; a full batch loops again at once with a beat, and each pass still takes a batch from every enabled table, so one backlog never starves another. The progress budget stays 300 seconds.
- `workspace_mirror` (`app/services/workspace_mirror_worker.py`): every `WORKSPACE_MIRROR_INTERVAL_SECONDS` it pages the OpenClaw agents, system agents included, in `running`, `idle`, `stopped` and `error` (50 per page, in id order) and calls `mirror_agent` for each whose state directory exists, up to `WORKSPACE_MIRROR_CONCURRENCY` agents at once and never two of one organization. It beats as each agent finishes and after every page, a logged agent failure included, and a database error reading a page retries in place with capped backoff (1 to 30 seconds) and no beat. With no durable store (local storage, or `WORKSPACE_MIRROR_ENABLED=false`) it pages nothing and beats after each interval sleep. `progress_budget_seconds()` is the interval plus `PAGE_READ_SECONDS` (60) plus one `AGENT_SECONDS` (140: the 20-second pass budget, which starts when the agent's slot is granted, plus 120 for the operation in flight), because some agent is always finishing. The start path does not run this loop: it pulls through `agent_materialize.pull_durable_state` under the exclusive setup lock it already holds.
- Restart is opt-in: `OwnedTasks.start_supervised(name, factory, progress_budget_seconds=, policy=RestartPolicy(budget, max_backoff_seconds, before_restart))` takes a coroutine factory and owns a `<name>-supervisor` task beside the incarnation. The supervisor waits for the incarnation to finish (error, normal return or cancellation outside shutdown), logs `Restarting required loop <name>` with the error, sleeps `capped_backoff` (1 s doubling up to the ceiling; `OwnedTasks(clock, sleep)` injects both), awaits `before_restart`, then starts a fresh coroutine. Never restart from a done-callback and never reuse a coroutine. It never starts one once `closing` is set; `stop()` cancels supervisor and incarnation. `restarts[name]` counts restarts used and `exhausted` holds loops that gave up. The budget is per process lifetime: once `restarts[name]` reaches it the next exit is final (logged with name and error, `exhausted` gains the name and the dead task keeps readiness red); a failing `before_restart` or factory also lands in `exhausted`. A restarted loop is unready until its first real `loop_progress().beat()` (`LoopProgress.restarted()`; `exempt()` exits are not beats), so a crash-looping worker never flaps green. Stale progress is only reported, never restarted. `lifecycle.py` opts in `auth_email` and `broadcast_email` with `WORKER_LOOP_RESTART_BUDGET` (default 5) and `WORKER_LOOP_RESTART_MAX_BACKOFF_SECONDS` (default 30); their `before_restart` is `system_email_service.wait_for_abandoned_sends`, which waits until no `attempt_email` SMTP thread left behind by the old incarnation is still running. Loops that do not opt in behave as before: dead stays dead until the process restarts.
- `EventTasks` tracks admitted SDK callbacks; closing rejects new callbacks with `CancelledError`, then cancels/awaits existing callbacks. Do not let callbacks outlive their manager's ownership.
- Readiness requires initialized, not draining, an API/worker/connector role, satisfied required tasks, and API realtime subscription readiness when applicable.
- Probe existing pool and Redis concurrently with separate two-second bounds; probes must not initialize resources. Skip probes while ineligible and recheck eligibility after them to catch draining/subscription races.
- `/api/ready` returns 200 `{"status":"ready"}` or 503 `{"status":"not_ready"}`; never leak driver/credential details. `/api/health` remains the independent pool-only check.
- `/api/live` (`readiness.py`, mounted by `main.py`) is the Docker `HEALTHCHECK` target: it never touches the pool or Redis, answers 200 `{"status":"alive"}`, and returns 503 `{"status":"failed"}` only once `OwnedTasks.exhausted` is non-empty; a hung event loop makes it time out. A restarting, merely unready or stale loop stays alive, so a database blip never replaces replicas. The `HEALTHCHECK` has `--start-period=120s` because uvicorn listens only after lifespan startup (pool, bootstrap, connector setup).

### Auth email operations

- Settlement retries the same fenced database update, never SMTP: at most three writes per claim and ten seconds total, clipped to the remaining lease and batch budget. A fence miss stops retries. If settlement stays unresolved, the worker logs the job ID and a safe failure class, finishes the batch, and keeps scanning. Check oldest pending jobs and expired leases alongside these warnings. An uncommitted settlement can leave an already delivered message eligible to send again after lease expiry, if the credential is still current. The stable `Message-ID` does not guarantee deduplication.
- Alert on sustained `GET /api/ready` 503s for each worker-capable process. The Docker healthcheck calls `/api/live`: it stays green while the supervised mail loops crash and restart, and fails only after one spent its restart budget, so the container is replaced. Unexpected loop failures and every restart or give-up are logged by task name and offered to the runtime incident reporter when enabled. After the dependency recovers, a live worker resumes scans without a restart; an exit (for example, after an SMTP batch timeout) is restarted by the supervisor after waiting for abandoned SMTP threads, and unready until its first finished batch.

## Shutdown And Connectors

- Mark draining and synchronously close trigger/heartbeat/inbox-wake admission before teardown so readiness fails immediately and producers refuse new work. Stop route background work, owned wrappers, schedule executions and connector managers, then drain trigger invocations, heartbeats and native per-agent drains (`openclaw_routing` inbox-wake admission), then shut the guest Docker lane (`shutdown_docker_capacity`: drops queued calls and never joins a hung CLI's thread) before proxy, realtime subscriber, pool, Redis, LLM clients, outbound and Tavily HTTP pools, pooled MCP sessions (`shutdown_mcp_sessions`: one best-effort DELETE per same-loop session within two seconds, then each client closed; entries from an earlier loop are dropped unawaited), and logging. Each producer drain waits within its grace period, then cancels and awaits only its owned work. Native cancellation joins and reaps the local Docker CLI before payload cleanup or guest exclusion release, even under repeated cancellation; it does not prove cancellation of a detached Gateway run. Use attempted-resource flags to clean partial acquisition.
- `Runtime.stop` fits `SHUTDOWN_CLEANUP_BUDGET_SECONDS` (`shutdown_budget.py`). Each step may run until its scheduled end, so unused time carries forward but never into the tail reserved for pool, Redis, LLM, outbound, Tavily, MCP and logging. `_cleanup` runs a step as a task and stops waiting at its slice without cancelling it: an `asyncio.timeout` around a step or `stop` is no bound, since `drain_on_cancel` absorbs it. Drains get half their slice as grace; joins inside a step stop at 90% of it. A new step needs a share in `STEP_SHARES` or `TAIL_SHARES`, and the container stop timeout must cover `SHUTDOWN_HTTP_GRACE_SECONDS` + budget + 10 s (Fargate max 120 s).
- Shield the cleanup task with both AnyIO cancellation shielding and `asyncio.shield`; repeated task cancellation must not interrupt cleanup. Await completion, preserve an original failure, otherwise re-raise cancellation. Each cleanup boundary logs failures/cancellation and continues.
- Feishu, DingTalk, WeCom, WeChat and Discord all run under `ReconcileRuntime`; no manager owns its own pass loop. The finite `setup` task is the first `reconcile_clients` pass, retried in place with capped backoff (1 to 30 seconds) until it succeeds, so a transient database error delays readiness and `transfer_cleanup` instead of failing them. It then registers the required `<provider>-reconcile` loop: every 30 seconds one pass, the same in-place retry without a beat, and a beat only after a pass whose configuration read succeeded. A successful setup return must not be classified as a dead required loop.
- A pass fails only when its configuration read fails. The stream managers' `reconcile_clients` run `channels/stream_reconcile.py`: rows map through the never-raising `desired_stream_source`; missing, finished or changed clients start, revoked ones stop, an unchanged source is never restarted, and one agent's failure is logged and backed off per agent while the pass goes on. Per-agent lifecycle locks serialize start, stop and pass decisions. A DingTalk thread still alive after its stop join is stopping, not live: later passes retry the stop and never open a second connection beside it. WeCom writes `channel_configs.is_connected` on connect and stop and re-asserts it every pass; its status route reads that column.
- `Runtime.start` opens every manager; `begin_drain` closes them before any cleanup awaits, so neither a pass nor a post-save start opens a client after drain. `Runtime.stop` cancels the reconcile loops with the owned wrappers before each manager's `stop_all`.
- `transfer_cleanup` first awaits every required finite setup task inside `loop_progress().exempt(restart_on_error=False)`, then runs `start_transfer_cleanup_reconciler()` (a one-second polling loop). It beats only when `reconcile_transfer_cleanup()` returns `True`; that returns `False` only when the pending queue could not be read, never beats itself, and its other callers ignore the result. `whatsapp_personal` (`personal_supervisor`) starts immediately, beats after each finished `candidates()` pass (a failed pass backs off without a beat), and spawns the Node bridge per claimed connection; bridge children never beat. Its contract is `../services/channels/AGENTS.md`.
- No connector startup from request handlers or before pool initialization. A handler saves or deletes the row first and calls one `start_client`/`stop_client` only when `role_enabled(parse_process_roles(PROCESS_ROLE), "connector")`; otherwise the connector's next pass applies the row (engine-wide rule).

## Proxy Resource Boundary

- Connector proxy setup is optional: missing ss-local skips; unusable nodes warn and skip. Nodes come from `SS_CONFIG_FILE` (default `/data/ss-nodes.json`), otherwise `SS_SERVER`/`SS_PASSWORD` settings when the file is absent.
- Keep credentials in the temporary config passed as `ss-local -c <path>`. Shield subprocess creation so cancellation still records the process for cleanup; publish `DISCORD_PROXY=socks5h://127.0.0.1:1080` only after the child survives startup. Save the previous env value before publishing.
- Failed/cancelled unpublished attempts shield cleanup, stop the child and unlink config. Shutdown terminates/waits five seconds, then kills/waits five seconds if needed; finally unlink config, clear ownership and restore the previous `DISCORD_PROXY` or remove it if originally absent.
- Successful finite proxy setup is not an ongoing subprocess-liveness probe. Keep connector proxy env separate from the sandbox guest `SANDBOX_*_PROXY` trust boundary.
